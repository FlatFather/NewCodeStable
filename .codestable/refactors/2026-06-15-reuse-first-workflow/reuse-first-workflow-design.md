# CodeStable 工作流"复用优先"系统性优化方案

## 问题现状

**用户反馈**：
> 工作流在使用的时候产出的方案偏新增逻辑，而不是根据现有的业务逻辑去扩展优化

**典型案例**：
- 需求："根据 shopno 查询店铺 ID"
- AI 设计：新增 `get_shop_id_from_db()` 函数
- 用户质疑：现有 `get_shop_name_from_db()` 已经在查同一张表，为什么不合并？
- 问题：AI 没有主动发现可复用的现有函数

**根因分析**：
1. **复用分析缺失** — 没有专门环节评估复用机会
2. **时机太晚** — implement 阶段才深入读代码，方案已定
3. **没有分流** — 不区分"全新功能"和"扩展现有"
4. **缺少复用文化** — 提示词没有强调"复用优先"

---

## 优化目标

建立"复用优先、扩展为主、新增为辅"的工作流文化：

| 优先级 | 策略 | 判据 |
|--------|------|------|
| P0 | 复用现有 | 现有函数/模块能满足需求 |
| P1 | 扩展现有 | 现有函数/模块可扩展（加参数/加分支） |
| P2 | 新增代码 | 现有无法复用，必须新建 |

**量化目标**：
- 80% 的功能应优先考虑扩展现有代码
- 新增函数前必须有"为什么不复用"的显式理由
- 减少用户手动指出复用机会的频率

---

## 优化方案：三大改动

### 改动 1：在 design 前增加"复用分析"强制步骤

**当前流程**：
```
brainstorm → design → plan → implement → accept
```

**优化后**：
```
brainstorm → [复用分析] → design → plan → implement → accept
                ↑
            新增强制步骤
```

**"复用分析"步骤内容**：
1. **关键词提取**：从需求提取 3-5 个核心词（名词/动词）
2. **代码搜索**：用 fast-context / grep 搜索关键词
3. **产出"复用清单"**：
   ```markdown
   ## 复用清单
   
   ### 可直接复用
   - 函数 A (file.py:123)：功能描述
   
   ### 可扩展后复用
   - 函数 B (file.py:456)：功能描述 → 扩展方式：加参数 X
   
   ### 不可复用（需新增）
   - 搜索了关键词 X/Y/Z，无相关代码
   - 或：函数 C 不可复用，原因：职责不匹配
   ```

**实施方式**：
- 选项 A：在 `cs-feat-design` 启动检查中强化（轻量级）
- 选项 B：独立出 `cs-feat-explore` 技能（重量级）

---

### 改动 2：design 模板增加"复用与扩展策略"章节

**在现有 design 模板的第 1 节后增加**：

```markdown
### 第 1.5 节：复用与扩展策略

**复用清单**（来自启动步骤的复用分析）：
- 函数 A：直接复用
- 函数 B：扩展后复用 → 扩展方式：XXX

**本次策略**：
- [ ] 复用为主（≥70% 逻辑复用现有代码）
- [ ] 扩展为主（在现有模块基础上扩展）
- [ ] 新增为主（必须新增，理由：XXX）

**新增理由**（如果有新增函数）：
每个新增函数/模块必须回答：
- 为什么不复用现有 X？
- 为什么不扩展现有 Y？
```

**强制性**：
- 如果选择"新增为主"，必须填写详细理由
- 如果复用清单有"可扩展"项，优先选择扩展

---

### 改动 3：cs-feat 路由增加"扩展 vs 新增"分诊

**当前路由逻辑**：
```
cs-feat → 判断有无 design → 有 → 继续；无 → 创建
```

**优化后路由逻辑**：
```
cs-feat → 分诊问题："这是全新功能还是扩展现有功能？"
         ↓
    ┌────┴────┐
    │         │
  全新     扩展现有
    │         │
    ↓         ↓
 design   [复用分析] → design
```

**分诊问题示例**：
- "你想做的是一个全新的功能模块，还是在现有功能上扩展？"
- 判断信号：
  - "加个 XX 功能" → 可能是扩展
  - "优化 XX 逻辑" → 扩展
  - "新建 XX 系统" → 全新
  - "给 XX 增加 YY 能力" → 扩展

## 各阶段具体改动

### cs-feat-design 启动检查强化

**改动位置**：`cs-feat-design/SKILL.md` 第 157-176 行

**当前第 3 条**：
```markdown
3. **读需求相关的现有代码**——读哪些文件由需求线索决定
```

**改为**：
```markdown
3. **相关代码搜索与复用分析**（强制，必须产出复用清单）：
   
   a. **关键词提取**：
      - 从需求中提取 3-5 个核心关键词（名词/动词）
      - 示例：需求"根据 shopno 查询店铺 ID" → 关键词：shop, shopno, query, db, id
   
   b. **代码搜索**（优先级顺序）：
      - 优先：fast-context 语义搜索（"查询店铺信息"）
      - 备选：grep 精确搜索关键词
      - 范围：函数名、类名、注释、文档
   
   c. **复用清单产出**（必须格式）：
      ```markdown
      ## 复用清单
      
      搜索关键词：shop, shopno, query, db
      
      ### 可直接复用
      - get_shop_name_from_db (utils/db.py:123)
        功能：根据 shopno 查询 basic_shop_info 表返回 shop_name
        复用方式：直接调用
      
      ### 可扩展后复用
      - get_shop_name_from_db (utils/db.py:123)
        功能：同上
        扩展方式：修改返回值为 (shop_id, shop_name) 元组
        兼容性：保持向后兼容（可选参数控制返回格式）
      
      ### 不可复用（需新增）
      - 搜索了 shop/query/db，未找到查询店铺 ID 的函数
      - get_shop_info() 存在但职责是缓存层，不可复用
      ```
   
   d. **复用判断规则**：
      - 同表查询 → 优先合并查询
      - 类似逻辑 → 优先提取公共函数
      - 职责相近 → 优先扩展现有模块
   
   **最小产出要求**：
   - 必须产出上述格式的复用清单
   - 找到 ≥1 个相关函数，或明确说明"搜索了 X/Y/Z，无相关代码"
   - 如果有"可扩展"项，必须在 design 中优先考虑扩展方案
```

**新增按信号触发条**：
```markdown
- **复用机会提醒**——复用清单有"可扩展"项时，在 design 第 1.5 节必须优先设计扩展方案；如果最终选择新增，必须在第 1.5 节写明"为什么不扩展 X"的理由
```

### cs-feat 路由逻辑增加分诊

**改动位置**：`cs-feat/SKILL.md` 第 65-95 行

**当前逻辑**：
```markdown
判断产物状态 → 路由到对应阶段
```

**增加分诊问题**（在路由前）：
```markdown
## 分诊：扩展 vs 新增

**触发时机**：用户触发 cs-feat 且无已有产物时

**分诊问题**：
> 我理解你想做：{AI 复述需求}。
> 这是一个全新的功能模块，还是在现有功能上扩展？

**判断信号**：
- 触发词：加、增加、优化、改进、扩展 → 偏向扩展
- 触发词：新建、创建、搭建、从零 → 偏向全新
- 不确定：问用户

**路由规则**：
- 全新功能 → brainstorm / design（正常流程）
- 扩展现有 → **强制复用分析** → design
  - 复用分析产出清单 → 传递给 design
  - design 第 1.5 节基于清单设计
```

### design 模板增加第 1.5 节

**改动位置**：`cs-feat-design/reference.md` 模板

**插入位置**：第 1 节"决策与约束"之后

**新增内容**：
```markdown
### 第 1.5 节：复用与扩展策略

**复用清单**（来自启动步骤第 3 条）：
- 函数 A (路径)：功能描述 → 复用方式：直接复用 / 扩展后复用
- 函数 B (路径)：功能描述 → 不可复用原因：XXX

**本次策略**（三选一）：
- [ ] 复用为主（≥70% 逻辑复用现有代码）
- [ ] 扩展为主（在现有模块基础上扩展，新增 <30% 代码）
- [ ] 新增为主（必须新增独立模块/函数）

**策略说明**：
- 如果选择"扩展为主"：
  - 列出扩展点：在哪个函数/模块的哪个位置扩展
  - 兼容性保证：如何保证不破坏现有调用
  - 示例：在 get_shop_name_from_db 增加可选参数 include_id=False
  
- 如果选择"新增为主"：
  - 必须逐项说明：为什么不复用清单中的每个"可扩展"项
  - 新增理由必须是以下之一：
    - 职责不匹配（具体说明）
    - 扩展会破坏现有逻辑（具体说明）
    - 性能考量（具体说明）
    - 清单中无相关代码

**扩展点设计**（如果选择扩展）：
- 扩展点 1：函数 A.参数 X
  - 默认值：保持向后兼容
  - 新增逻辑：描述
- 扩展点 2：模块 B.新增函数 C
  - 为什么放在 B 而不是新建？理由：XXX
```

### plan 阶段增加复用验证

**改动位置**：`cs-feat-plan/SKILL.md`

5. **复用策略验证**：
   - 读取 design 第 1.5 节的策略

   - 如果是"新增为主"，验证 design 是否有充分理由
```

**plan 模板调整**：
```markdown
## 推进顺序

### 如果是"扩展为主"：
1. 读取现有函数 X 的实现
2. 设计扩展方案（参数/分支）
3. 验证兼容性（跑现有测试）
4. 实施扩展
5. 补充测试

### 如果是"新增为主"：
1. 确认无法复用（复查 design 1.5 节理由）
2. 设计新函数/模块
3. ...
```

### accept 阶段增加复用审查

**改动位置**：`cs-feat-accept/SKILL.md` 验收报告

**新增第 2.5 节**：
```markdown
## 2.5 复用策略审查

对照 design 第 1.5 节：

**策略执行验证**：
- [ ] design 声明策略：{复用为主 / 扩展为主 / 新增为主}
- [ ] 实际执行：{描述}
- [ ] 是否一致：✓ / ✗ (如不一致，说明原因)

**复用清单核对**：
- [ ] design 列出的"可扩展"项是否都评估了？
- [ ] 如果最终没扩展，理由是否充分？

**过度新增检查**：
- [ ] grep 项目中是否有类似函数被遗漏？
- [ ] 新增函数是否可以合并到现有模块？

**复用率统计**（可选）：
- 复用现有代码行数：X 行
- 新增代码行数：Y 行
- 复用率：X / (X+Y) = Z%
```

## 预期效果

| 指标 | 当前 | 优化后 |
|------|------|--------|
| 复用分析覆盖率 | 0%（无此步骤） | 100%（强制） |
| 用户手动指出复用 | 高频 | 低频 |
| 新增 vs 扩展比例 | 8:2（新增为主） | 3:7（扩展为主） |
| 设计返工率 | 中（实现时发现复用点） | 低（设计时已评估） |

---

## 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 流程变长 | 启动变慢 | 复用分析只需 2-3 分钟 |
| 误判"可扩展" | 扩展失败需返工 | design 阶段可推翻复用清单 |
| 过度强调复用 | 该新增时不敢新增 | "新增为主"是合法选项，只需理由充分 |
