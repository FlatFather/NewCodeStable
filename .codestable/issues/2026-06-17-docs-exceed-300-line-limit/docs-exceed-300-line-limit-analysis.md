# 4 个核心文档超过 300 行限制 根因分析

## 1. 问题定位

| 关键位置 | 说明 | 超标原因 |
|---|---|---|
| `cs-feat-design/SKILL.md:1-369` | feature design 主技能文档 | 包含完整流程 + 启动检查 + 三个入口模式 + 详细的复用优先机制说明 |
| `cs-feat-design/reference.md:1-352` | feature design 参考模板 | 包含 frontmatter 格式 + design/plan/checklist 三种产物的完整模板 + 各节写作要求 |
| `cs-feat-accept/SKILL.md:1-311` | feature acceptance 主技能文档 | 包含验收报告模板 + 9 个核对节的详细说明 + 退出条件 |
| `cs-refactor/reference/methods.md:1-394` | 重构方法参考库 | 包含 L1-L4 四个层级共 25 种重构方法的完整说明 |

## 2. 失败路径还原

**正常路径**：技能文档编写时考虑 300 行限制 → 内容超长时主动拆分 → 通过引用关联拆分后的文件 → 符合规范

**失败路径**：技能文档编写时追求"一个文件包含所有信息" → 内容持续累积（特别是 2026-06-15 reuse-first 机制新增） → 未触发拆分检查 → 超过 300 行限制

**分叉点**：各技能文档编写时，没有设置"接近 300 行时拆分"的守护机制

## 3. 根因

**根因类型**：missing-guard（缺少防御机制）

**根因描述**：

项目在 CLAUDE.md 中明确规定"单 md 文档不能超过 300 行，超过必须拆分"，但在实际技能文档编写过程中：

1. **缺少拆分触发机制**：没有在文档编写时设置接近 300 行的提醒或强制拆分检查点
2. **内容自然增长**：随着功能迭代（特别是 2026-06-15 reuse-first 机制的引入），文档内容持续累积
3. **一体化倾向**：技能文档编写时倾向于"把相关内容放在一起方便查阅"，忽略了可读性和维护性的平衡点

**是否有多个根因**：单一根因（缺少防御机制），但有 4 个独立的超标案例

## 4. 影响面

- **影响范围**：
  - 直接影响：4 个核心技能文档违反编码规范
  - 间接影响：AI 读取超长文档时上下文效率下降，可能影响技能执行质量
  - 潜在风险：如果不修复，后续技能文档可能继续超标（没有形成拆分意识）

- **潜在受害模块**：
  - 其他正在编写或将要编写的技能文档
  - 依赖这些技能的用户工作流体验

- **数据完整性风险**：无（纯文档问题，不涉及数据损坏）

- **严重程度复核**：**维持 P1**
  - 理由：虽然不阻塞功能运行，但这 4 个文档都是高频使用的核心技能，影响面较大；同时违反明确的编码规范，需要尽快修复以建立拆分文化

## 5. 修复方案

### 方案 A：按内容模块垂直拆分（推荐）

**做什么**：
1. **cs-feat-design/SKILL.md** (369行) → 拆为 3 个文件：
   - `SKILL.md` (核心流程 + 启动检查，约 200 行)
   - `initialization-mode.md` (初始化模式详细说明，约 80 行)
   - `reuse-analysis-guide.md` (复用分析机制详细说明，约 90 行)

2. **cs-feat-design/reference.md** (352行) → 拆为 3 个文件：
   - `reference-frontmatter.md` (frontmatter 规范，约 80 行)
   - `reference-templates.md` (design/plan/checklist 模板，约 150 行)
   - `reference-writing-guide.md` (各节写作要求，约 120 行)

3. **cs-feat-accept/SKILL.md** (311行) → 拆为 2 个文件：
   - `SKILL.md` (核心流程 + 启动检查，约 150 行)
   - `acceptance-checklist-guide.md` (9 个核对节详细说明，约 160 行)

4. **cs-refactor/reference/methods.md** (394行) → 拆为 4 个文件：
   - `methods-overview.md` (方法索引 + 用法速查，约 50 行)
   - `methods-L1-L2.md` (L1 行为等价迁移 + L2 代码级重构，约 150 行)
   - `methods-L3.md` (L3 结构拆分，约 120 行)
   - `methods-L4.md` (L4 性能与异步，约 80 行)

**优点**：
- 符合"单一职责"原则，每个文件聚焦一个主题
- 拆分后文件大小均衡，便于维护
- 保持原有逻辑结构，改动最小

**缺点 / 风险**：
- 需要更新技能内部的文档引用路径
- 用户首次查阅时需要了解新的文档组织结构

**影响面**：
- 会动 4 个主文件 + 新增 9 个拆分文件
- 为保持运行时引用正确，还会补 3 个入口/索引文件的引用路径（`cs-feat-plan/SKILL.md`、`cs-refactor/SKILL.md`、`cs-refactor-ff/SKILL.md`）
- 不影响技能对外接口和用户调用方式

---

### 方案 B：按使用频率水平拆分

**做什么**：
- 每个超标文档拆为"核心 + 扩展"两部分
- 核心部分保留在原文件，包含最常用的内容（约 250 行）
- 扩展部分移到 `{原文件名}-advanced.md`，包含详细说明和边缘案例

**优点**：
- 高频使用场景不受影响（核心文件内容不变）
- 拆分策略简单统一

**缺点 / 风险**：
- "核心"与"扩展"的边界不清晰，可能导致逻辑割裂
- 扩展部分可能被忽略，降低文档完整性
- 长期维护时核心部分可能再次超标

**影响面**：
- 会动 4 个主文件 + 新增 4 个扩展文件
- 需要在每个核心文件末尾增加"进阶内容"索引

---

### 方案 C：引入健康度检查工具 + 最小拆分

**做什么**：
1. 先增加 `.codestable/tools/check-doc-length.sh` 脚本，定期检查文档长度
2. 只拆分当前最超标的 2 个文档（cs-refactor/reference/methods.md 394行，cs-feat-design/SKILL.md 369行）
3. 其余 2 个文档（352行、311行）暂时保留，待下次内容新增时再拆分

**优点**：
- 增加预防机制，避免未来再次超标
- 最小化当前改动范围

**缺点 / 风险**：
- 只解决部分问题，剩余 2 个文档仍违反规范
- 可能被视为"治标不治本"

**影响面**：
- 会动 2 个主文件 + 新增工具脚本 + 新增约 5 个拆分文件

---

### 推荐方案

**推荐方案 A**，理由：

1. **彻底解决问题**：一次性处理所有 4 个超标文档，符合项目规范
2. **改动范围可控**：虽然涉及 4 个技能，但每个技能的拆分逻辑清晰，不会引入复杂的依赖关系
3. **建立拆分文化**：通过这次系统性拆分，为后续技能文档编写树立范例
4. **维护性最佳**：按内容模块拆分后，每个文件职责单一，未来修改时影响面最小
5. **符合 CodeStable 设计哲学**：项目强调"可演进、可观测、可控制"，方案 A 的拆分策略与此理念一致
